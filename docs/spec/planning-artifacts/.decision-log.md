### DEC-001: Reimagined as an Enterprise Wrapper for Open-Source Frameworks (BMAD)

*   **Date of Decision:** 2026-03-18
*   **Status:** Approved
*   **Deciders / Contributors:** Eric Maxwell (Author/PM), APF Ninja (Market Researcher), Enterprise Architecture Board
*   **Problem Statement / Context:**
    The original vision of the Agentic Product Lifecycle Platform (APLP) was conceived as a custom modular AI agent chain (consisting of Scaffold, RFC, Security, and Ops agents) triggered via background API integrations and managed within an Internal Developer Platform (IDP) state engine. 
    
    However, this design presented severe adoption and operational roadblocks:
    1.  **The IDE Lock-in:** Highly powerful, community-proven AI agent methodologies (like BMAD) were confined entirely to developer terminals and IDE setups. This completely excluded key non-technical personas (Product Managers, UX Designers, and System Architects) from direct, real-time collaboration with agents during critical upstream planning phases.
    2.  **The "Accountability Vacuum":** Storing planning specs solely inside decoupled database state machines isolated them from the primary code branches. There was no single, immutable, and easily-audited Git record linking product decisions, system designs, and code commits.
    3.  **High Proprietary Maintenance Tail:** Custom building, chaining, and fine-tuning bespoke modular agents required immense platform engineering overhead and created highly fragile systems that broke under standard LLM API updates.

*   **Alternatives Considered:**
    *   **Option 1: Continue with Custom Proprietary Agentic Toolchains**
        *   *Pros:* Complete internal control over internal agent behaviors; zero external third-party open-source dependency.
        *   *Cons:* Fails to provide visual-first interfaces requested by UX/PM roles; extreme engineering and context-maintenance overhead; locked to specific models.
    *   **Option 2: Transition to a Sandboxed Enterprise GUI Platform Wrapper for Open-Source Standards (BMAD)**
        *   *Pros:* Leverage highly refined open-source agent scripts (e.g. `bmad-pm`, `bmad-ux`, `bmad-architect`); extend capabilities beyond the terminal via a collaborative visual workspace embedding standard modeling suites; establish standard **Git-centric repository sync** to bind specs directly to code trees. (Chosen)

*   **Decision & Rationale:**
    Adopt **Option 2**. Reimage APF as an Enterprise Enablement Platform wrapping open-source agent frameworks, standardized around the BMAD methodology:
    1.  **Democratized GUI Canvas:** Move interaction loops from terminal commands to a collaborative GUI Console incorporating live preview panes, visual pipeline tracking, and interactive chat.
    2.  **Git-Centric Continuity:** All agent-human planning artifacts (PRDs, user flow diagrams, topography schemas) are synced continuously back to the repository under `design-artifacts/`. This provides a continuous, reviewable context chain that automatically hydrates developer workspaces (like AntiGravity) upon cloning.
    3.  **Model Context Protocol (MCP) Integration:** Adopt MCP to sand-box visual editor frames (specifically Draw.io, Lucidchart, Figma, and Google Stitch) inside platform web iframes, securing high-speed state synchronization without leaking private browser context.

*   **Risks & Mitigations:**
    *   **Risk:** Deep dependency on the open-source BMAD project roadmap and execution updates.
        *   *Mitigation:* Construct pluggable, framework-agnostic backend adapters that interface with agent runs, isolating core platform interfaces.
    *   **Risk:** Security vulnerabilities, authorization leaks, and server execution escapes from autonomous agents mutating workspace files.
        *   *Mitigation:* Implement absolute organization VPC isolation, run detached proxy nodes for execution routines, and ensure human approval gates are required before code merges.

*   **Validation & Review Status:**
    Validated by comprehensive market research matching APF's positioning against low-code visual AI tools and observability buffers (Vellum, MindStudio, Dust). Approved by the Enterprise Architecture Board on 2026-03-18.

### DEC-002: Activity Stream Robustness & Reconnection History (Story 2.2)

*   **Date of Decision:** 2026-05-13
*   **Status:** Approved
*   **Deciders / Contributors:** Eric Maxwell (Author), `bmad-architect` (Story 2.2 Adversarial Reviewer)
*   **Problem Statement / Context:**
    During development and adversarial review of Epic 2 (Story 2.2: Live Cross-Agent Activity Feed), severe robustness defects were detected in handling browser network disruptions and event broadcast pipelines:
    1.  **Disconnection History Purge:** When a user experienced a transient socket drop (common in corporate Wi-Fi transitions), the client automatically reconnected but flushed the active notification drawer, deleting existing historical context feeds.
    2.  **Client-Side Timing Heuristics:** The client relied on client-side timestamp calculations to deduce whether an incoming feed element was "historical" or "live." This was highly vulnerable to client system clock drift, creating sorting failures.
    3.  **Implicit Broadcasts:** Endpoint transitions (such as platform validator warnings or agent save triggers) failed to publish events to the global stream, causing separate persona tabs to fall out of sync.

*   **Alternatives Considered:**
    *   **Option 1: Client-Side Cache Buffering**
        *   *Pros:* Minimal backend structural change; buffers events in local client storage.
        *   *Cons:* Chronological sorting remains vulnerable to clock drift; fails under persistent browser state clears or incognito canvas runs.
    *   **Option 2: Explicit Lifecycle Broadcast Hooks & Server-Side Metadata Tagging**
        *   *Pros:* Resolves clock-drift race conditions; ensures historical logs persist on the server and survive transient re-connections. (Chosen)

*   **Decision & Rationale:**
    Expand `FR-1.2 Activity Stream` with detailed, robust sub-requirements to fix these vulnerabilities:
    1.  **FR-1.2.1 Lifecycle Broadcast Hooks:** Force all backend endpoints managing platform workflow steps and state transitions to explicitly broadcast activity stream events.
    2.  **FR-1.2.2 Server-Side Metadata Tagging:** Require the backend to explicitly tag and categorize messages as historical, completely eliminating client-side clock heuristics.
    3.  **FR-1.2.3 Reconnection History Preservation:** Mandate that socket re-connections keep and re-populate existing notification drawer items.
    *Rationale:* This prevents UI fragmentation and ensures complete data integrity across remote, multi-persona workspace canvases, securing the reliability of the platform's auditable activity trail.

*   **Risks & Mitigations:**
    *   **Risk:** High database read/write costs and traffic surges in Firestore from broadcasting minor canvas interactions.
        *   *Mitigation:* Strictly limit broadcast messages to high-level system state transitions (pipeline progress, verification logs, manual saves) rather than active cursor tracking or typing changes.

*   **Validation & Review Status:**
    Validated, tested, and locked under adversarial code review evaluation. Approved and integrated into the functional spec on 2026-05-13.

### DEC-003: User Settings Secrets Security (JWE & Dependency Injection) (Story 2.3)

*   **Date of Decision:** 2026-05-14
*   **Status:** Approved
*   **Deciders / Contributors:** Eric Maxwell (Author), Scrum Master, Technical Architect, `bmad-dev` (Amelia), `bmad-code-review` validators (Blind Hunter, Edge Case Hunter, Acceptance Auditor)
*   **Problem Statement / Context:**
    Following the initial backend development for Story 2.3 (User-Level Secrets Settings Screen), an exhaustive tripartite adversarial review (Blind Hunter, Edge Case Hunter, Acceptance Auditor) identified 4 critical "Bad Spec" security flaws and 12 "Patch" code defects that compromised secure architectural principles:
    1.  **Plaintext Storage Context:** While Firestore database-at-rest encryption was enabled, third-party user keys (Figma, Lucidchart, Stitch integration credentials) were stored in plain text relative to the database context itself, creating severe exfiltration risks under platform role compromise.
    2.  **Proprietary Non-Standard Encryption String:** Secrets transmission from the central orchestrator to detached agent proxies used a home-grown concatenated key token string (`jwe-encrypted-enclave-token:<cek>.<nonce+ciphertext>`) that standard JWE libraries could not parse.
    3.  **Discarded Ephemeral Private Key:** The dev/test fallback routine generated a temporary RSA keypair in memory when environment keys were absent but discarded the private key. This guaranteed cryptographic decryption failures in detached dev/test proxy runtimes.
    4.  **Decryption Lockout Risk:** Firestore ciphertext lacked key version headers (e.g. `v1:`), making decryption impossible upon key rotation. Furthermore, decryption failure returned direct API failures that permanently locked users out from revoking or updating corrupted keys.
    5.  **Clean Architecture Violation:** Secret HTTP handlers relied on package-level global states rather than struct-based dependency injections, blocking unit testing and CI test parallelization.

*   **Alternatives Considered:**
    *   **Option 1: Complete Story Under Old Specs & Track Refactoring as Post-Sprint Debt**
        *   *Pros:* Keeps the current Sprint 2 roadmap unchanged.
        *   *Cons:* Deploys severe, active security vulnerabilities into the project's staging environment, blocking standard automated integration tests.
    *   **Option 2: Course Correction Sprint Change Proposal**
        *   *Pros:* Immediately updates specifications across the PRD, Architecture, and Story documents, followed by executing 12 precise backend code refactors. Enforces strict compliance with industry security standards upfront. (Chosen)

*   **Decision & Rationale:**
    Adopt **Option 2 (Sprint Change Proposal)**. The PRD functional specs (`FR-1.3`), core Architecture, and Epics were refactored to require:
    1.  **FR-1.3.1 Application-Level secret encryption:** Mandate AES-256-GCM application-layer encryption before persistence, incorporating explicit key version headers (`v1:`), and graceful reset fallbacks to prevent permanent lockout.
    2.  **FR-1.3.2 Standard JWE Compact Serialization:** Enforce standard compact serialization (`eyJ...`) using compliant cryptographic libraries, alongside pre-shared dev/test public-private key pairs to prevent key-pair discarding.
    3.  **FR-1.3.3 Lifecycle Actions & Dependency Injection:** Refactor all secrets, chat, and session HTTP handlers into struct receivers, completely eliminating package globals.
    *Rationale:* Mitigates database-layer data-theft vectors, aligns the orchestrator with standard cryptographical serialization specs, secures human OIDC credential routing, and establishes Clean Go package dependencies.

*   **Risks & Mitigations:**
    *   **Risk:** Increased development effort during Sprint 2, threatening existing feature schedules.
        *   *Mitigation:* Scope changes specifically to secret data brokers in `api/` modules; leverage robust Go-native cryptographic libraries (`go-jose`) to execute refactors rapidly.

*   **Validation & Review Status:**
    Formally evaluated and validated under `bmad-code-review`. Integrated into specs and confirmed by the Scrum Master and Technical Architect via a Sprint Change Proposal on 2026-05-14.

### DEC-004: Decoupling PRD from Platform Implementation Leakage

*   **Date of Decision:** 2026-05-14
*   **Status:** Approved
*   **Deciders / Contributors:** Eric Maxwell (Author), BMad PRD Quality Validator
*   **Problem Statement / Context:**
    During automated PRD quality validation pipelines, a "Warning" block detected severe implementation detail leakage within the Functional Requirements:
    1.  **FR-1.2.2:** Dictated that historical event filtering on the client must be driven by a backend database metadata flag explicitly named `isHistorical` (a boolean).
    2.  **FR-1.3.1:** Mandated the specific backend database system `Firestore` and concrete encryption algorithm strings.
    
    Specifying exact database platforms and naming boolean property keys in the core PRD restricts the engineering and architecture teams' ability to adapt or migrate backend infrastructures (e.g., migrating to Spanner, SQL, or custom Redis layers) without triggering spec-level changes.

*   **Alternatives Considered:**
    *   **Option 1: Retain Specific Stack Names**
        *   *Pros:* Gives clear stacks for backend developers.
        *   *Cons:* Blurs the boundary between business expectations (WHAT) and technical realization (HOW). Breaks PRD traceability standards.
    *   **Option 2: Generalize Functional Requirements & Push Technical Specs to downstream design docs**
        *   *Pros:* Retains the pure functional boundary of product requirements while preserving technical stacks inside architectural files. (Chosen)

*   **Decision & Rationale:**
    Apply simple fixes validation updates to remove "Firestore" from `FR-1.3.1` (generalizing it to "persisting to database records") and decouple `FR-1.2.2` from specific database boolean names (requiring "server-provided metadata tagging"). 
    
    *Rationale:* A high-quality PRD must remain implementation-agnostic. Removing proprietary stack lock-in preserves modularity, allowing product specifications to focus purely on business and user outcomes. Implementation stack parameters are preserved inside architectural blueprints and downstream developer tasks.

*   **Risks & Mitigations:**
    *   **Risk:** Engineering has less direct blueprints on initial tool and library targets.
        *   *Mitigation:* Keep detailed references to Firestore, Google Stitch integrations, and cryptographic algorithms under the down-stream architectural designs and specific story tasks (e.g. Story 2.3).

*   **Validation & Review Status:**
    Validated by the BMad Implementation Leakage compliance checker. Merged into the finalized PRD on 2026-05-14.

### DEC-005: Concrete Measurability and Telemetry Gating for NFRs

*   **Date of Decision:** 2026-05-14
*   **Status:** Approved
*   **Deciders / Contributors:** Eric Maxwell (Author), BMad PRD Quality Validator
*   **Problem Statement / Context:**
    Initial drafts for Non-Functional Requirements (NFR-1.1, NFR-1.2, NFR-3.1) lacked measurable metrics and business context. They defined critical operational baselines in subjective terms (e.g., "fast GUI load speeds," "low-latency updates," and "highly concurrent workspace scaling"). This introduced two high-severity risks:
    1.  **Unverifiable Release Gates:** Staging and QA engineers could not define precise binary (pass/fail) automated verification tests.
    2.  **Context-Free Performance Goals:** Developers lacked concrete explanations for *why* latency targets were set, leading to poor prioritization of browser/socket tuning tasks.

*   **Alternatives Considered:**
    *   **Option 1: Maintain Qualitative SLAs**
        *   *Pros:* Minimal upfront profiling; keeps requirements flexible for fast prototyping.
        *   *Cons:* High risk of user performance degradation; renders automated load-testing blocks completely impossible.
    *   **Option 2: Formulate Strict Telemetry Targets and Embed Business Impact**
        *   *Pros:* Secures high-performance, predictable client and backend scaling; forces the integration of load test hooks in the CI/CD pipeline. (Chosen)

*   **Decision & Rationale:**
    Restructure the NFR specifications to inject strict percentile-based targets, explicit verification tools, and the underlying business context:
    1.  **NFR-1.1 GUI Load Time:** Restructured to target `< 2 seconds for the 95th percentile` as measured by APM monitoring. Rationale: "To prevent user abandonment during workflow transitions".
    2.  **NFR-1.2 Sync Latency:** Restructured to target `< 100ms for the 95th percentile` as measured by WebSocket frame timing metrics. Rationale: "To enable seamless real-time multi-persona collaboration".
    3.  **NFR-3.1 Scalability (Concurrent Users):** Restructured to target `at least 50 concurrent users per active workspace session without degradation` as measured by distributed load testing suites. Rationale: "To support enterprise-scale deployment clusters".
    *Rationale:* Standardizing these ensures automatic quality gates can execute load and performance testing continuously, keeping the platform fast and responsive under high production loads.

*   **Risks & Mitigations:**
    *   **Risk:** Rigorous latency testing can add telemetry overhead and slow down non-production performance.
        *   *Mitigation:* Deploy comprehensive tracing blocks exclusively in testing environments and staging clusters, applying lightweight sampling rules in production.

*   **Validation & Review Status:**
    Validated by the BMad Measurability Checker. Verified, locked, and merged into the finalized PRD on 2026-05-14.

### DEC-006: Reconciliation of Story 2.3 Secrets Management Specifications with PRD Governance Standards

*   **Date of Decision:** 2026-05-21
*   **Status:** Approved
*   **Deciders / Contributors:** APF Ninja (Product Owner/Scrum Master), AntiGravity Partner Agent
*   **Problem Statement / Context:**
    The **Story 2.3 Backend Remediation & Course Correction Sprint Change Proposal** proposed extensive modifications to the PRD functional requirements under `FR-1.3` to secure user credentials. However, the initial draft of the change proposal introduced two direct violations of prior architectural decision [DEC-004: Decoupling PRD from Platform Implementation Leakage](/docs/specs/E-PRD/.decision-log.md#dec-004-decoupling-prd-from-platform-implementation-leakage):
    1.  **FR-1.3.1:** Hard-coded the specific cryptographic algorithm **`AES-256-GCM`** into the product-level requirements.
    2.  **FR-1.3.3:** Injected explicit Go programming language syntax, struct declarations, and backend database package symbols `(e.g., type SecretsHandler struct { store db.UserSecretsStore })` directly into the product specifications.
    
    Mandating language-specific programming structures and explicit encryption algorithms inside the business requirements limits modularity and prevents developers from refactoring packages, adopting alternative implementation patterns, or performing vector migrations without mutating product-level customer contracts.

*   **Alternatives Considered:**
    *   **Option 1: Direct Integration (Path B)**
        *   *Pros:* Extremely explicit code blueprints directly in the primary requirement file.
        *   *Cons:* Direct violation of the decoupling rule validated under DEC-004; couples product definition to Go-specific infrastructure; triggers product-level changes on minor backend variable updates.
    *   **Option 2: Strict Governance Gating (Path A)**
        *   *Pros:* Strips implementation detail leakage (AES-256-GCM and struct receiver code snippets) from [APF_Foundry_PRD.md](/docs/specs/E-PRD/APF_Foundry_PRD.md), representing them as high-level functional bounds. Forces the concrete code specifics into the technical context maps: [architecture.md](/docs/specs/planning-artifacts/architecture.md) and [2-3-user-level-settings-screen.md](/docs/specs/implementation-artifacts/2-3-user-level-settings-screen.md). Preserves purity of requirements. (Chosen)

*   **Decision & Rationale:**
    Adopt **Option 2**. Fully reconcile the PRD specifications by generalizing the requirements to strong application-level encryption (`FR-1.3.1`) and global-free decoupled dependency injection (`FR-1.3.3`), stripping code snippets and exact cryptographic algorithms. Push the specific implementation parameters down into [docs/spec/planning-artifacts/architecture.md](/docs/specs/planning-artifacts/architecture.md) (Group 2) and [docs/spec/implementation-artifacts/2-3-user-level-settings-screen.md](/docs/specs/implementation-artifacts/2-3-user-level-settings-screen.md) (Group 4).
    
    *Rationale:* Keeping the PRD implementation-agnostic preserves long-term platform modularity and guarantees a clean, professional, and audit-ready requirements standard. Developer specifications retain maximum clarity through downstream context files without cluttering high-level business definitions.

*   **Risks & Mitigations:**
    *   **Risk:** Developers might lose connection to implementation directives if onboarding solely from the PRD.
    *   **Mitigation:** The decision log establishes explicit cross-references pointing directly to the technical blueprints in `architecture.md` and `2-3-user-level-settings-screen.md`.

*   **Validation & Review Status:**
    Approved collaboratively via interactive conflict reviews between the Product Owner and the Partner Agent on 2026-05-21.

### DEC-009: Complete Removal of Direct Sync Route Requirement

*   **Date of Decision:** 2026-05-30
*   **Status:** Approved
*   **Deciders / Contributors:** Antigravity (AI Coding Assistant), APF Ninja (Product Owner), Enterprise Security Lead
*   **Problem Statement / Context:**
    The initial requirements for Epic 4 included a "Direct Sync Route" option where agents could directly commit and push changes to the primary repository branch (e.g., `main`) without peer review or staging gates. Under enterprise deployment audits, allowing autonomous agents or external triggers to bypass branch protection rules and merge code directly without explicit human approval presents severe security and supply-chain risks.
*   **Alternatives Considered:**
    *   **Option 1: Retain Direct Sync as an Optional/Developer Mode toggle**
        *   *Pros:* Speeds up automated prototyping sequences in dev namespaces.
        *   *Cons:* Bypasses enterprise zero-trust governance; violates automated staging controls; highly risky under compromised user identities.
    *   **Option 2: Delete the Direct Sync Route and enforce gated Pull Request flows exclusively**
        *   *Pros:* Guarantees a mandatory "human-in-the-loop" peer review gate for every workspace synchronization step, adhering strictly to enterprise compliance. (Chosen)
*   **Decision & Rationale:**
    Adopt **Option 2**. Completely eliminate the "Direct Sync Route" requirement from all specifications and codebase systems. All synchronization operations must target dedicated target feature/artifact branches and initialize standard Pull Requests (PRs) enforcing review gates (`FR-4.2`).
*   **Risks & Mitigations:**
    *   **Risk:** Minor increase in manual click overhead for fast development iterations.
    *   **Mitigation:** Streamline the PR creation response UI, providing deep links in canvas Snackbars to instantly access and approve changes.
*   **Validation & Review Status:**
    Approved and validated under the zero-trust security review gate on 2026-05-30.

### DEC-010: AI-Tier Git Push Alignment and API-Tier Streamlining

*   **Date of Decision:** 2026-05-30
*   **Status:** Approved
*   **Deciders / Contributors:** Antigravity (AI Coding Assistant), APF Ninja (Product Owner), Lead Backend Engineer
*   **Problem Statement / Context:**
    The original Story 4.3 design assumed that the API tier must perform the Git push operation during remote VCS synchronization. However, a physical codebase and architectural audit revealed that the local Git commit and remote push sequence is already executed automatically in the AI tier via the file-writing interceptor plugin (Story 4.1). Having the API tier run duplicate Git pushes introduces concurrency conflicts, branch-locking races, and code duplication.
*   **Alternatives Considered:**
    *   **Option 1: Retain duplicate push routines in both tiers**
        *   *Pros:* Redundant safeguard.
        *   *Cons:* Causes branch conflicts, workspace locking failures, and excessive network operations.
    *   **Option 2: Align roles: AI-tier handles files/push, API-tier verifies and initializes PRs**
        *   *Pros:* Establishes clean division of concerns. Streamlines the API tier's role to verify branch presence and gracefully handle pending sync states. (Chosen)
*   **Decision & Rationale:**
    Adopt **Option 2**. Streamline the API-tier Story 4.3 scope: remove redundant git push operations and re-focus the endpoint to perform dynamic remote branch verification and grace-fail pending states.
*   **Risks & Mitigations:**
    *   **Risk:** Dependency on the AI-tier interceptor successfully pushing.
    *   **Mitigation:** API-tier endpoint performs preflight verification and reports descriptive pending warnings instead of crashing if the push has not completed.
*   **Validation & Review Status:**

### DEC-011: Automated Onboarding and Project Discovery Workflow

*   **Date of Decision:** 2026-05-30
*   **Status:** Approved
*   **Deciders / Contributors:** APF Ninja (Product Owner), Antigravity (AI Coding Assistant), Enterprise Architect
*   **Problem Statement / Context:**
    Enterprise teams adopting BMad currently face massive cognitive friction when attempting to onboard pre-existing (brownfield) codebases, manually creating planning spec folders and copying context file-by-file. To solve this adoption blocker, APF needs an automated discovery engine that scans and catalogs legacy projects, maps existing requirements files to active BMad enclaves, and guides the user through an interactive verification wizard during launch.
*   **Alternatives Considered:**
    *   **Option 1: Fully Automated Bootstrapping (No Human Gate)**
        *   *Pros:* Zero-click onboarding.
        *   *Cons:* Fails to capture user preference regarding which directories or legacy briefs are active or out-of-scope, generating stale requirements mappings.
    *   **Option 2: Gated Lifecycle-Driven Onboarding (Chosen)**
        *   *Pros:* Establishes three clear state lifecycles (`New` -> `Onboarding` -> `Onboarded`). Enforces an interactive selection grid where the user confirms stack discovery, handles pre-existing specs via read-only/overwrite toggles, and explicitly marks onboarding complete.
*   **Decision & Rationale:**
    Adopt **Option 2**. This guarantees absolute human-in-the-loop control over the ingestion context. Standardizing the `Onboard` Project Dashboard tile cues for projects in the `New` or `Onboarding` states ensures complete UI clarity and allows users to pause and resume onboarding sessions dynamically without losing state. If the background scan fails, onboarding is completed as a minimal/new setup, preventing user blockout.
*   **Risks & Mitigations:**
    *   **Risk:** Overwriting existing specs in a legacy repo.
    *   **Mitigation:** Detected existing BMad specs are pre-selected and flagged, providing an explicit toggle: "Keep Existing Spec (Read-Only)" or "Re-Reconcile & Overwrite".
*   **Validation & Review Status:**
    Validated via joint PO/Architect socratic refinement rounds. Approved on 2026-05-30.
